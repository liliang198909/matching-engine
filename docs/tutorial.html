01先建立一个直觉

交易所里没有"自动成交"这回事，所有成交都来自某个人主动接受别人的报价。撮合引擎要做的只有两件事：

  • 排队：没人接的订单按价格、按时间排进订单簿。
  • 配对：新来的订单如果和对面能对上，就按对方的价格成交，一直吃到对不上或自己吃完为止。

整个项目就是把这两件事做成一个可以公网访问、重启不丢数据的服务。剩下的 HTTP、PostgreSQL、WebSocket 都是在它外面加的三层壳：

层回答什么问题去掉会怎样
engine谁能和谁成交、成交多少、成交价是多少项目不存在
api外部怎么提交、查询、撤销订单只能写 Go 代码调用
store进程重启后数据从哪里回来一重启订单全丢
/ws客户端怎么不用轮询就看到变化只能不停问接口
一句话记法：engine 是大脑，api 是柜台，store 是账本，ws 是广播喇叭。

02三层嵌套的数据结构

订单簿不是一张平表，而是"抽屉里还有抽屉"：

Orderbook
├── Bids []*Limit            买盘，价格从高到低
├── Asks []*Limit            卖盘，价格从低到高
├── BidLimits map[float64]*Limit   价格 → 档位（买）
└── AskLimits map[float64]*Limit   价格 → 档位（卖）

Limit（一个价格档位，例如"卖 100"）
├── Price        float64
├── Bid          bool
├── Orders       []*Order    同一价格上排队的订单，先来先成交
└── TotalVolume  float64     该档位剩余总量

Order（一笔委托）
├── ID        uint64
├── Size      float64    剩余未成交数量（会变小）
├── Price     float64    委托价（永不变）
├── Bid       bool
├── Timestamp int64
└── Limit     *Limit     指回所在档位；离开档位后置 nil

为什么这样设计

  • 为什么要两层索引？撮合永远只看最优价，用有序切片取首元素是 O(1)；而撤单要先按价格找到档位，用哈希表也是 O(1)。两套索引指向同一批 Limit，所以必须由 Orderbook 一个对象统一维护，不能各存一份。
  • 为什么 Orders 用切片不用链表？新单永远追加到尾部，天然就是时间优先；撮合只从头部取，也很自然。
  • 为什么删除要保序？常见做法是与尾部交换做到 O(1)，但那会打乱到达顺序，直接破坏"同价先到先成交"。这里故意用 O(n) 换正确性，面试时这是个很好的取舍点。
  • 为什么 Order.Price 和 Limit 要各存一份？订单离开档位后 Limit 会被清空，此时查单仍要知道它挂的什么价。

Engine 上还挂着四样东西

字段作用没有它会怎样
mu一把互斥锁，串行化所有读写并发下单直接数据竞争
index订单 ID → 订单指针撤单要扫全簿
statuses订单 ID → 生命周期状态成交后查不到历史订单
trades全部成交记录没有历史成交接口

statuses 是很容易被忽略的一层：订单一旦成交或撤销就不在订单簿里了，但客户端仍然要能查到结果，所以状态必须独立保存。

03亲手点一次撮合

下面这个小盘口和真实引擎用同一套规则：价格优先、同价时间优先、成交价取被动方（先挂单方）的价格。提交几笔订单，看盘口和成交是怎么变化的。

订单簿模拟

成交价永远是挂单方的价格，不吃点差
卖盘 Asks · 价低优先
    买盘 Bids · 价高优先
      提示：卖单挂 100×5、102×3，买盘 99×2

      观察三件事：

      1. 买 102×4 时，先吃 100 这一档（价格优先），成交价是 100 而不是 102。
      2. 如果 100 档有两笔单，先挂的那笔先成交（时间优先）。
      3. 没吃完的剩余量会变成一笔新的挂单，进入对面盘口排队。

      04撮合循环只有十来行

      真实代码在 engine/engine.go。把注释剥掉，主干就这么点：

      func (e *Engine) submitLocked(id uint64, size, price float64, bid bool) []Trade {
    o := NewOrder(id, size, bid)
    o.Price = price

    var filled []Trade
    if bid {
        filled = e.matchBid(o, price)      // 买单去扫卖盘
    } else {
        filled = e.matchAsk(o, price)      // 卖单去扫买盘
    }

    if !o.IsFilled() {
        e.book.PlaceOrder(price, o)        // 没吃完就挂上
        e.index[o.ID] = o
    }
    e.trades = append(e.trades, filled...)
    return filled
}

      matchBid 是一个循环，每一轮：

      1. 取对面最优档位；如果价格已经不交叉，直接退出。
      2. 取该档位最早的一笔订单，成交量 = min(剩余量, 对方剩余量)。
      3. 生成一笔成交，双方剩余量同时扣减。
      4. 如果对方被吃满，从档位删除；档位空了，整个档位移除。
      5. 自己吃满了就结束，否则继续下一轮。
      成交价为什么取对方的价格？因为先挂单的人先做出了价格承诺，后到的人只能接受。这也解释了为什么市价大单会一路吃到更差的价位（滑点）。

      每一次 fill 还会同步更新被动方在 statuses 里的累计成交量和剩余量——状态表不是事后算的，而是随撮合一起维护的。

      05HTTP 层：把函数变成服务

      api 包不了解撮合细节，它只做四件事：解析 JSON、校验参数、调引擎、编码响应。引擎也完全不知道 HTTP 的存在——这条边界让两边都能独立修改。

      POST   /orders          下单，返回本次产生的成交
GET    /orders/{id}     查订单状态（open / filled / cancelled）
DELETE /orders/{id}     撤单
GET    /depth?n=5       盘口前 n 档
GET    /trades?limit=&offset=   历史成交分页
GET    /ws              WebSocket 实时推送
GET    /healthz         健康检查

      几个值得记住的实现细节：

      • 路由用 Go 1.22 的"方法 + 路径"模式，方法不对时标准库自动返回 405，不用手写判断。
      • 根路径写成 GET /{$} 而不是 GET /，否则它会变成兜底路由，把所有未知路径都接住，404 就废了。
      • 参数错误一律 400 并说明原因，不做"静默用默认值"的兜底。
      • 响应使用独立 DTO，而不是直接序列化引擎类型，避免协议绑死内部字段名。

      06持久化：只存事件，不存结果

      很多实现会存"订单表 + 成交表"，这里只有一个 events 表，记录两类事件：下单和撤单。

      CREATE TABLE events (
    id         BIGSERIAL PRIMARY KEY,
    kind       TEXT NOT NULL CHECK (kind IN ('order', 'cancel')),
    side       TEXT CHECK (side IN ('buy', 'sell')),
    price      DOUBLE PRECISION CHECK (price > 0),
    size       DOUBLE PRECISION CHECK (size > 0),
    cancel_id  BIGINT,
    created_at TIMESTAMPTZ NOT NULL DEFAULT now()
);

      启动时按 id 顺序把这些事件重放一遍，订单簿和成交历史就原样回来了。之所以可行，是因为撮合是确定性的：同样的输入顺序，必然得到同样的结果。

      两个关键顺序问题

      • 先落库，再改内存。写库失败就返回 503 且不动内存；反过来的话，会出现"内存有、库里没有"，重启后账本对不上。
      • 下单和撤单必须共用同一个序列。否则回放时只能"先放所有下单、再放所有撤单"，与真实的交错顺序不一致，订单会复活或消失。

      订单 ID 由数据库序列分配，所以进程重启后编号仍然连续、不撞号；引擎内部的 seq 只在纯内存模式下使用。

      07实时推送：为什么轮询不够

      盘口每秒都可能变，客户端每秒问一次接口既慢又浪费。WebSocket 建立一条长连接，服务端主动推：

      连上           → {"type":"depth","depth":{...}}        先给一份快照
有人挂单       → {"type":"depth","depth":{...}}        盘口变了
发生成交       → {"type":"trade","trade":{...}}        逐笔成交
               → {"type":"depth","depth":{...}}        新的盘口
      • 盘口推的是全量快照而不是增量，客户端直接覆盖本地状态即可，丢一帧也不会错位。
      • 每个订阅者一个有界缓冲通道，发送是非阻塞的：某个浏览器卡住，只丢它自己那一帧，撮合主流程绝不等网络。
      • 先订阅、再发首帧快照，堵住"快照写完到订阅生效之间"的变化空窗。

      08面试里最可能被追问的八个问题

      价格优先和时间优先分别是怎么保证的？

      价格优先靠 Bids/Asks 两个按价格排序的切片，撮合永远取首元素。时间优先靠档位内 Orders 的插入顺序：新单追加到尾部，撮合从头部取；删除时保序，不与尾部交换。

      下单和撤单的复杂度是多少？

      下单 O(k)，k 是被扫过的档位数，每档还要做一次常数级撮合；撤单 O(1) 定位（靠 index）+ O(m) 保序删除（m 是档内订单数）；查单与深度都是 O(1) 和 O(n)。

      并发安全怎么做的？会不会有性能问题？

      整个引擎一把互斥锁，等价于"单写者模型"：所有变更串行执行，读也加锁。实现简单、语义清楚，代价是多核无法并行撮合。要扩容通常是分交易对/分片，而不是把单簿拆锁——同一订单簿的撮合本身就要求全序。

      为什么不用"订单表 + 成交表"？

      两张表写入存在半成功风险，且成交是撮合的推导结果，重复存储会有一致性问题。只存事件、启动回放，天然满足崩溃一致性，也只有一个事实来源。

      重启时怎么保证状态和崩溃前一模一样？

      因为撮合是确定性的，回放相同顺序的事件必然得到相同状态。前提是下单与撤单共用同一序列，保证交错顺序可还原；并且先落库再改内存，保证内存状态是库状态的子集。

      回放会不会越来越慢？

      会，目前是 O(事件数) 的启动成本，适合演示规模。生产做法是周期性打快照 + 只回放快照之后的事件。

      WebSocket 慢客户端会不会拖垮服务？

      不会。广播是序列化一次、非阻塞分发；每个连接有 16 条缓冲，满了就跳过这一帧。盘口是全量快照，下一帧自动收敛；成交推送丢了也能用 /trades 补。

      这个项目离生产还差什么？

      市价单与改单、账户与资金校验、快照加速启动、鉴权与限流、多副本与故障切换。这些都能在 README 的 Possible Extensions 里找到。
